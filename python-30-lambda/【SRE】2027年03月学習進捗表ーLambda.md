## この期間の位置づけ

boto3 は「**boto3からLambdaを操作する**」側（一覧取得・invoke・設定更新・同時実行数・エイリアス）でした。ここからは「**Lambdaの中で動かす**」側です。

**boto3スクリプトのLambda化は省略します。** ハンドラの形・実行ロール・環境変数・デプロイパッケージ・EventBridge定期実行は、この教材の `eventbridge_scheduled_job.py` を1本やれば全部通るためです。移植工程を挟むと「Lambdaは運用スクリプトの実行台」という偏った捉え方が残るので、最初からイベント駆動で入ります。

**この期間の主眼は、イベントソースごとに `event` の構造がまったく違うことを手で確かめること**です。教材には7種類（EventBridge / S3 / API Gateway / Cognito / SQS / DynamoDB Streams / Step Functions）入っています。ここがLambda開発の本体です。

### アプリの位置づけ

12月〜3月と同じ形式の四択アプリを併用します。**日程も14本の構成も変えず、各日の冒頭10〜15分をアプリに充てます。**

アプリで問うのは「**コードを読めば答えられること**」に限定しました。`event` の構造、戻り値の形、実行ロールとリソースベースポリシーの向きの違い、`TypeDeserializer` が要る理由、`batchItemFailures` のキー名、`resource` と `client` の型の扱い、といった論点です。

**実行して初めて分かることは出題していません。** 次の5つはアプリではなく手で確かめてください。答えを先に見ると実機の価値が失われます。

- ハンドラ外のコードがコールドスタートで何回走るか（3/17）
- `ReportBatchItemFailures` の有効／無効で再試行される件数がどう変わるか（3/31）
- インメモリの `_processed_ids` が同時実行で破綻すること（4/4）
- VPC に入れた Lambda がインターネットに出られないこと（4/8）
- `body` を dict のまま返したときに実際に返るもの（3/22）

boto3 と同じく、**全問を最初に1周する期間は設けていません。** サービスが1ヶ月に散らばっているため、そのジャンルを扱う当日に初見で解き、翌日以降にコンボまで持っていく流れにしています。例外は横断ジャンルの **01（実行基盤とハンドラ・8問）** で、ここは全14本の土台なので第1期の最初の3日でコンボまで終わらせます。

## デプロイ方式

**Terraformで統一します。** すでに書けることが理由です。**毎回コンソールから手で作らないでください。** 14本ぶん繰り返すと、学習ではなくクリック作業になります。

**14本ぶんの定義は `環境-Terraform.zip` に書き上がっています**（`modules/lambda_fn/` に「Lambda関数＋実行ロール＋ロググループ」の型があり、`stage1〜stage7.tf` が各サンプルをその型で呼び出す形）。したがって日々の【環境】作業は「ゼロから書く」ではなく、**型と stage を読む → 該当フラグを `true` にして `apply` する → 演習のために一部を外して挙動を見て、戻す**という流れになります。読まずに apply だけすると何も残らないので、**その日に触る stage ファイルは必ず開いてください。**

※第4期のVPCも `stage6_rds.tf` に専用のものが書かれています（**プライベートサブネットのみ。IGW も NAT も作らない**）。boto3 期間のセットAの VPC を持ち込むと 4/8 の「VPC Lambda は外に出られない」実測が成立しなくなるので、流用はしないでください。

イベントの中身を見る作業には、**マネジメントコンソールのテストイベント機能**を使ってください。S3・SQS・API Gateway・DynamoDB Streams などのサンプルイベントがテンプレートとして用意されており、実際のトリガを構成する前に `event` の構造を確認できます。

```bash
# CLI から任意のイベントを流し込む場合
aws lambda invoke --function-name my-fn \
  --payload file://event.json --cli-binary-format raw-in-base64-out out.json
```

## 前提：アプリのランク機構

12月〜3月の演習アプリと同じ仕組みです。

| ランク | 到達条件 |
|---|---|
| ミス | 初期状態、または直近で誤答 |
| ジャブ | 1回連続正解 |
| ヒット | 2回連続正解 |
| コンボ | **3回連続正解** |

**誤答するとランクは一発でミスに戻ります。** 初見の1周だけではコンボにならないため、**14ジャンルすべてを3日にわたって回す**割り当てにしてあります（初見「全て」→「コンボを除く」→ コンプリート）。

出題パターンの使い分け：

- **「全て」** … そのジャンルの初見。現在地の把握。**調べない。**
- **「コンボを除く」** … 2日目以降の潰し込み。コンプリート表示が出るまで回す。

誤答した問題は、解説に出ている**参照ファイルの該当箇所を開いて突き合わせる**ところまでが1セットです。

履歴はブラウザのローカル領域にしか残りません。**各期末（3/21・3/28・4/4・4/11・4/14）に「学習成績」画面から JSON を書き出すこと。** 12月〜3月のアプリとは保存キーが別なので、履歴が混ざることはありません。

### 1日の型

**冒頭10〜15分：アプリ**

1. その日に新しく出てくるジャンルを**「全て」**で1周する（初見の日のみ。**調べない**）
2. 前日までに出たジャンルを**「コンボを除く」**で回し、コンプリート表示を目指す
3. 誤答した問題は、解説を読んだうえで**参照ファイルの該当箇所を開いて突き合わせる**

**残り時間：コードと実機**

4. コードを読み、**`event` に何が入ってくるか**を先に書き出す
5. コンソールのテストイベントか `aws lambda invoke` で流し込み、**予想と実際の差**を確認する
6. 実トリガを構成して動かす
7. **CloudWatch Logs を必ず開く。** ログを見ない日はゼロにする

アプリが15分で終わらない日は**そこで打ち切って実機を優先**します。残りは翌日の冒頭と 4/14 の総ざらいで回収します。逆に実機が早く終わった日は、余った時間を未コンボの潰し込みに充ててください。

### 凡例：作業種別タグ

各項目の先頭に、その作業が何をするものかを示すタグを付けています。**時間が足りない日は【環境】【実機】【改造】を優先し、【読解】【説明】【アプリ】を翌日か期末に回してください。**

| タグ | 何をするか | 溢れたときの扱い |
|---|---|---|
| **【環境】** | Terraform でリソースを作る・変える・消す | **落とせない。** 以降の日が止まる |
| **【実機】** | AWS 上で実際に動かして目で確かめる | **落とせない。** 環境を消した後ではやり直せない |
| **【改造】** | 教材のコードに手を入れる | **落とせない。** 4/4 がこの月の中心 |
| **【読解】** | コードを読む、`event` の構造を書き出す | 翌日の冒頭に回せる |
| **【説明】** | 言語化して説明できる状態にする | 期末のまとめ日（3/28・4/14）に回せる |
| **【アプリ】** | 四択アプリ（冒頭10〜15分） | 翌日の冒頭と 4/14 の総ざらいで回収する |
| **【記録】** | JSON書き出し、済チェック、引き継ぎメモ | 期末の分は落とさない |

**【環境】が付いた日は、その日の最初に `terraform apply` を流してください。** 待ち時間を【アプリ】に充てる前提で組んであります。どのフラグを `true` にするかは `【SRE】Lambdaテスト環境構築手順.md` の日別手順にあります。

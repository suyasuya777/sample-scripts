# SRE 実務スキルマップ（ネットワーク編 / セキュリティ編）

- 対象: SRE として実務に入る際に必要となるネットワーク・セキュリティ知識の棚卸し
- 優先度の基準: アラート対応・障害調査・日常運用で触れる頻度（優先度「中」のジャンルは本書では対象外）
  - **最高** … 一次切り分けで問われる。手薄だと調査が止まる
  - **高** … 設計・改善フェーズで必須
- 使い方: 左端の `□` は項目全体の済管理、学習のポイント欄の `□` は個別の合格基準の済管理。すべて `☑` に書き換えて進める
- **合格基準の考え方**: 「読んで分かった」では不合格。**声に出して説明できる**、または**実際にコマンドを打って確認した**状態を合格とする

# 第1部 ネットワーク編

## 1. トランスポート層（TCP / UDP） 〔優先度: 最高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | 3ウェイハンドシェイク | SYN → SYN/ACK → ACK で接続を確立する手順 | □ 「無応答でタイムアウト」＝経路かSGでの破棄、「即座にConnection refused」＝宛先にプロセスが待ち受けていない、と症状だけで切り分け先を即答できる<br>□ `tcpdump -i any 'tcp[tcpflags] & (tcp-syn) != 0'` で実際に3パケットを観測したことがある<br>□ SGで拒否した場合とNACLで拒否した場合でクライアント側の見え方がどう違うか説明できる |
| □ | TIME_WAIT | 接続を閉じた側が一定時間ソケットを保持する状態 | □ `ss -Htan state time-wait \| wc -l` で実数を数えられる（`-H` を付けないとヘッダ1行を数えてしまう）<br>□ なぜ2MSL待つのか（遅延パケットの誤配送防止と、最終ACK消失時の再送対応）を説明できる<br>□ サーバ側とクライアント側のどちらにTIME_WAITが溜まるかを、closeを先に呼ぶのがどちらかで判断できる |
| □ | エフェメラルポート枯渇 | クライアント側の一時ポートを使い切る状態 | □ `sysctl net.ipv4.ip_local_port_range` で利用可能範囲を確認できる<br>□ 「接続先が1つに集中している場合」に枯渇しやすい理由を、5タプルの一意性から説明できる<br>□ 対処として範囲拡大よりもコネクション再利用（Keep-Alive、プーリング）を優先すべき理由を言える |
| □ | SNATポート枯渇 | NAT Gateway経由で送信元ポートを使い切る状態 | □ CloudWatchメトリクス `ErrorPortAllocation` を監視項目として設定できる<br>□ 同一宛先IP・ポートへの同時接続が約55,000で頭打ちになる仕組みを説明できる<br>□ 回避策としてVPCエンドポイント導入、NAT Gateway増設、接続再利用の3つを挙げ、それぞれの適用条件を言える |
| □ | コネクションプール | 接続を使い回す仕組み | □ 「プール最大数 × タスク数 ≦ DBの max_connections」の検算を実際の設定値でやったことがある<br>□ プールが枯渇したときアプリ側でどう見えるか（取得待ちタイムアウト）を説明できる<br>□ スケールアウト時にDB接続数が先に上限に当たる構造を図で描ける |
| □ | Keep-Alive / アイドルタイムアウト | 接続を維持する時間 | □ 担当システムのLB側とアプリ側のタイムアウト値を両方確認し、書き出したことがある<br>□ アプリ側をLB側より長くする鉄則の理由（LBが再利用しようとした接続をアプリが先に閉じると502）を説明できる |
| □ | バックログ / SYNキュー | 接続待ち行列 | □ `somaxconn` とアプリのlisten backlogの関係を説明できる<br>□ 溢れた場合にクライアントからは「接続タイムアウト」に見え、サーバのエラーログには何も残らないことを理解している |
| □ | 輻輳制御・ウィンドウサイズ | 送信量を調整する仕組み | □ 帯域遅延積（BDP）の概念を説明できる<br>□ 「遅延の大きい経路では帯域が余っていてもスループットが出ない」理由を言える（チューニング手順までは不要） |
| □ | UDPの特性 | 再送も順序保証もない | □ DNS、SNMP、syslog、一部のメトリクス転送がUDPであることを知っている<br>□ 「欠損してもエラーにならず、静かにデータが減る」ため、送信側と受信側の件数差で監視する必要があることを説明できる |

## 2. 名前解決（DNS） 〔優先度: 最高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | レコード種別（A / AAAA / CNAME / ALIAS / TXT / MX / NS） | 用途ごとのレコード | □ ゾーン頂点（example.com そのもの）にCNAMEを置けない理由をRFC上の制約から説明できる<br>□ ALIASレコードがその制約をどう回避しているか（権威サーバ側でAに解決して返す）を説明できる<br>□ TXTレコードがSPF・DKIM・ドメイン所有証明に使われることを知っている |
| □ | TTL | キャッシュ保持時間 | □ 切替作業の前に「何日前にTTLを何秒へ下げるか」を逆算する手順を持っている<br>□ TTLを下げてから切り替えるまでに、旧TTL分の待機が必要な理由を説明できる<br>□ `dig` の出力からTTLの残り秒数を読み取り、キャッシュ済みか否かを判断できる |
| □ | ネガティブキャッシュ | 存在しない応答もキャッシュされる | □ SOAレコードのminimum値が効くことを知っている<br>□ 「レコードを追加したのに引けない」際に、先に問い合わせてしまったことが原因だと疑える |
| □ | リゾルバ / 権威サーバ | 問い合わせ代行側と正解を持つ側 | □ `dig @8.8.8.8 example.com` と `dig @権威サーバ example.com` を打ち分けられる<br>□ 両者の結果が食い違ったとき「リゾルバ側のキャッシュが古い」と判定できる<br>□ 自分の環境がどのリゾルバを使っているかを `/etc/resolv.conf` で確認できる |
| □ | アプリ側のDNSキャッシュ | 実行環境が独自にキャッシュを持つ | □ JVMの `networkaddress.cache.ttl` がデフォルトで無期限になりうることを知っている<br>□ 「OSやリゾルバのTTLを短くしてもアプリだけ古いIPを掴み続ける」現象の原因を特定できる<br>□ 対処としてアプリ再起動かキャッシュ設定変更のどちらが必要か判断できる |
| □ | プライベートホストゾーン | VPC内部でのみ解決できるゾーン | □ VPC内からは解決でき、外部からは解決できない構成を説明できる<br>□ オンプレとの相互解決にResolver Endpoint（Inbound / Outbound）が必要なことを理解し、構成図を描ける |
| □ | ヘルスチェック連動ルーティング | 加重・フェイルオーバー・レイテンシベース | □ 「切替完了までの時間 = 障害検知時間 + TTL」という式で最悪ケースを試算できる<br>□ 加重ルーティングを使った段階的な移行手順を説明できる |
| □ | 名前解決の経路 | resolv.conf → VPCリゾルバ → 権威 | □ `dig +trace example.com` を実際に打ち、ルートサーバから順に辿る過程を読める<br>□ どの段階で失敗したかを出力から特定できる |

## 3. HTTP と上位プロトコル 〔優先度: 最高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | ステータスコードの切り分け | 4xxはクライアント起因、5xxはサーバ起因 | □ ALBアクセスログの `elb_status_code` と `target_status_code` の違いを説明できる<br>□ 「LBが生成した5xx」と「アプリが返した5xx」をログ上で区別する具体的な条件を書ける<br>□ 400/401/403/404/429 がそれぞれ何を意味し、どこを調べるべきかを即答できる |
| □ | 502 Bad Gateway | LBがバックエンドから不正な応答を受けた | □ 原因の筆頭がタイムアウト値の逆転（アプリ側が先に接続を閉じる）であることを説明できる<br>□ アプリのgraceful shutdown不備でデプロイ時に発生するパターンを説明できる<br>□ 実際に502を再現、または過去の発生ログを読んで原因を特定したことがある |
| □ | 503 Service Unavailable | 正常なターゲットが存在しない | □ 「ヘルスチェック全滅」と「ターゲット未登録・スケール不足」のどちらかを、ターゲットグループの状態から即判定できる<br>□ ALBが503を返す条件と、アプリが自発的に503を返す場合の区別がつく |
| □ | 504 Gateway Timeout | バックエンドが時間内に応答しない | □ ALBのidle timeout値と、アプリ処理時間のp99を突き合わせて評価できる<br>□ 504が出たとき、アプリ側のログに該当リクエストの処理完了記録が残っているかを確認する手順を持っている |
| □ | HTTP/2 の多重化 | 1接続で複数リクエストを並行処理 | □ 接続数が減ることでLBの分散が偏る仕組みを説明できる<br>□ 1接続の詰まりが同一接続上の全リクエストに波及すること（HOLブロッキング）を理解している |
| □ | gRPC | HTTP/2ベースのRPC | □ 長寿命接続のためターゲット単位の負荷が偏る理由を説明できる<br>□ 対策としてクライアント側ロードバランシングやサービスメッシュが使われることを知っている |
| □ | WebSocket | 双方向の長時間接続 | □ LBのアイドルタイムアウトで切断される問題と、Ping/Pongによる回避策を説明できる<br>□ スケールイン時に接続中クライアントをどう扱うかの設計論点を挙げられる |
| □ | 冪等性とリトライ | 再実行して安全かどうか | □ GET/PUT/DELETEが冪等でPOSTが非冪等である理由を説明できる<br>□ 非冪等な処理に安全にリトライするための冪等キー（Idempotency Key）の考え方を説明できる |
| □ | X-Forwarded-For 等のヘッダ | LB経由で元のクライアントIPを伝える | □ このヘッダが複数値になる場合、どれを信頼すべきか判断できる<br>□ クライアントが偽装できるため、信頼できるプロキシの手前で上書きする必要があることを説明できる |

## 4. TLS / PKI 〔優先度: 高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | TLSハンドシェイク | 鍵交換と暗号方式の合意 | □ `openssl s_client -connect ホスト:443` を実行し、出力から使用プロトコルと暗号スイートを読み取れる<br>□ ハンドシェイク失敗時、バージョン不一致か暗号スイート不一致かをエラーから判別できる |
| □ | 証明書チェーン | サーバ証明書 → 中間CA → ルートCA | □ `openssl s_client -showcerts` でサーバが送出している証明書の並びを確認できる<br>□ 中間CAの配信漏れが「ブラウザでは通るがcurlやJavaでは失敗する」形で出る理由を説明できる |
| □ | SNI | 1つのIPで複数ドメインの証明書を出し分ける | □ `openssl s_client -servername` の有無で返る証明書が変わることを実際に確認できる<br>□ SNI非対応クライアントにはデフォルト証明書が返る挙動を知っている |
| □ | 証明書の有効期限 | 失効すると全面停止する | □ 期限を監視する具体的な仕組み（メトリクス化、定期スクリプト、マネージド通知）を1つ以上設計できる<br>□ 内部通信用の自己署名・プライベートCA証明書も監視対象に含める必要があることを理解している |
| □ | ACM / 自動更新 | AWSのマネージド証明書 | □ DNS検証用CNAMEを削除すると自動更新が止まることを知っている<br>□ ACM証明書がエクスポートできない（＝EC2上のnginx等には直接使えない）制約を説明できる |
| □ | mTLS（相互TLS） | クライアント側も証明書で認証する | □ 通常のTLSとの違い（クライアント証明書の検証が加わる）を説明できる<br>□ クライアント証明書の配布と失効・更新が運用負荷になる点を指摘できる |
| □ | TLS終端位置 | LBで終端するか、バックエンドまで暗号化するか | □ LB終端の場合、バックエンド区間が平文になることの是非を要件から判断できる<br>□ 終端位置によってWAFやアクセスログで見える情報が変わることを説明できる |
| □ | 暗号スイート / TLSバージョン | 許可する組み合わせ | □ ALBのセキュリティポリシーを確認し、どのTLSバージョンを許容しているか答えられる<br>□ 古いバージョンを廃止する前に、アクセスログからクライアントのTLSバージョン分布を集計する手順を持っている |

## 5. 負荷分散・トラフィック制御 〔優先度: 最高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | ALB と NLB の違い | ALBはL7、NLBはL4で低遅延・固定IP | □ 「固定IPが必要」「TCP以外を扱う」「超低遅延」ならNLB、「パス・ホストで振り分ける」「WAFを使う」ならALB、と要件から選定理由を説明できる<br>□ NLBではクライアントIPが保持される一方、SGが直接は効かない等の挙動差を説明できる |
| □ | ヘルスチェック設計 | パス・間隔・閾値・タイムアウト | □ 「間隔 × 異常閾値」で最短の切り離し時間を計算できる<br>□ ヘルスチェックのパスをDB疎通まで含めるか否かの判断基準を説明できる（含めるとDB障害で全台落ちる）<br>□ 実際に担当システムの設定値を確認し、検知時間を算出したことがある |
| □ | コネクションドレイニング | 切り離し中のターゲットに猶予を与える | □ デプロイ時の5xxの多くがドレイニング不足とgraceful shutdown未実装に起因することを説明できる<br>□ 登録解除の遅延時間を、アプリの最長処理時間より長く設定すべき理由を言える |
| □ | スティッキーセッション | 同一クライアントを同じターゲットに固定 | □ 有効にすると負荷が偏り、スケールアウトの効果が落ちる理由を説明できる<br>□ 第一選択はセッションの外部化（Redis等）であると判断できる |
| □ | ターゲットグループ / 振り分けアルゴリズム | 振り分け先の集合と分散方式 | □ ラウンドロビンと最小未処理リクエスト数（LOR）で、処理時間にばらつきがある場合の偏り方がどう変わるか説明できる |
| □ | リトライとサーキットブレーカ | 失敗時の再試行と、連続失敗時の遮断 | □ リトライストーム（再試行が負荷を増幅し障害を長引かせる現象）を説明できる<br>□ 多段構成でリトライを重ねると、実際のリクエスト数が掛け算で増える構造を計算で示せる<br>□ 指数バックオフにジッタを加える理由を説明できる |
| □ | タイムアウトの階層設計 | クライアント > LB > アプリ > DB | □ 担当システムの各層のタイムアウト値を書き出し、逆転がないか点検したことがある<br>□ 逆転している場合に何が起きるか（下流が処理継続中に上流が諦め、リソースだけ消費）を説明できる |
| □ | ブルーグリーン / カナリアデプロイ | 段階的に切り替える手法 | □ 両方式の違いと、それぞれに必要なインフラコストを説明できる<br>□ ロールバックにかかる実測時間を把握している、または測る手順を持っている |
| □ | バックプレッシャ | 下流の能力に合わせて上流の流量を絞る | □ キューが無限に伸びて遅延が爆発する障害パターンを説明できる<br>□ 流量制限・キュー長上限・早期エラー返却のいずれかで受け止める設計を提案できる |

## 6. クラウドネットワーク設計 〔優先度: 高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | VPC / サブネット設計 | CIDR設計は後から変えにくい | □ 「想定最大タスク数 + ローリング更新中の一時増分 + 予備」から必要IP数を逆算できる<br>□ AWSが各サブネットで5つのIPを予約することを知っている |
| □ | ルートテーブル | 宛先ごとの経路表 | □ 疎通不可時に「SG → NACL → ルートテーブル → 宛先側」の順で点検する手順を持っている<br>□ より具体的なCIDRが優先される最長一致の原則を説明できる |
| □ | セキュリティグループ / NACL | SGはステートフル、NACLはステートレス | □ NACLでは戻り通信用にエフェメラルポート範囲の許可が必要な理由を説明できる<br>□ SGは許可のみ、NACLは拒否も書ける違いと、使い分けの判断基準を言える |
| □ | NAT Gateway | プライベートサブネットの外向き通信を仲介 | □ AZごとに配置しないとAZ障害で全断する構成上の理由を図で説明できる<br>□ データ処理料金が課金される点と、VPCエンドポイントでの削減余地を指摘できる |
| □ | VPCエンドポイント（Gateway / Interface） | AWSサービスへ内部経路で接続 | □ Gateway型（S3・DynamoDB、無料）とInterface型（ENI、有料）の違いを説明できる<br>□ 導入によってNAT Gatewayのコスト削減とSNATポート枯渇回避の両方が得られることを説明できる |
| □ | Transit Gateway / VPCピアリング | 複数VPCの相互接続 | □ ピアリングが推移的ルーティング不可であること（A-B、B-CがあってもA-Cは通らない）を説明できる<br>□ VPC数が増えた際にTransit Gatewayへ移行する判断基準を言える |
| □ | ハイブリッド接続（Direct Connect / VPN） | オンプレとの接続 | □ DX単独、DX冗長化、DX+VPNバックアップの3構成をコストと可用性で比較できる |
| □ | マルチAZ / マルチリージョン | 障害分離の単位 | □ AZ障害時に残りAZで全トラフィックを捌けるキャパシティがあるかを試算したことがある<br>□ マルチリージョン化のコストと、そこまで必要な要件（RTO/RPO）の関係を説明できる |

## 7. コンテナのネットワーク 〔優先度: 高〕

| 済 | キーワード | 簡易説明 | 学習のポイント（合格基準） |
|---|---|---|---|
| □ | awsvpcモード | タスクごとにENIとIPを割り当てる | □ 「同時タスク数 = 消費IP数」であることを理解し、サブネットサイズとの関係を計算できる<br>□ ローリング更新中は新旧タスクが並存し、一時的にIP消費が増えることを織り込める |

| □ | SIEM連携 | ログの横断的な相関分析 | □ 調査時間を縮めるには検索性（パーティション設計、フォーマット統一）が鍵であることを説明できる<br>□ 複数ログソースを突き合わせて時系列を再構成する手順を持っている |
| □ | 検知から対応までの導線 | アラートが放置されない仕組み | □ 各アラートについてオーナー・初動・エスカレーション先を定義できる<br>□ 対応不要なアラートは鳴らさない、という削減の判断ができる |
| □ | ログの保持コスト設計 | 保持期間と階層化 | □ 保持要件（法令・契約・調査実務）から期間を決める手順を説明できる<br>□ ストレージクラスの階層化で費用を抑える設計ができる |

# 学習の進め方メモ

## 優先順位

**まず「最高」の7ジャンルから**着手します。ネットワークではトランスポート層・DNS・HTTP・負荷分散・可観測性、セキュリティではIAMとシークレット管理。ここが揃えば一次切り分けは回せます。

## 合格基準の付け方

学習のポイント欄の各行は、次のいずれかの形式で書いてあります。

| 語尾 | 求められる状態 | 確認方法 |
|---|---|---|
| 〜を説明できる | 他人に口頭で説明できる | 実際に声に出して説明してみる。詰まったら不合格 |
| 〜を計算できる / 試算できる | 数値を出せる | 手元の環境の実値で計算してみる |
| 〜を書ける | コマンド・クエリ・設定を書ける | 調べずに骨格を書けるか試す |
| 〜したことがある | 実際に手を動かした経験がある | 未経験なら検証環境で一度やる |

「調べれば分かる」は不合格です。障害対応中に調べる時間はありません。

## 補足

- **キャパシティ・制限値（第1部9章）は軽視されがち**です。負荷試験やスパイク障害の原因は、アプリのバグではなくクラウド側のソフトリミットであることが多くあります
- **サプライチェーン・CI/CD統制（第2部3章）は情報処理安全確保支援士の試験範囲外**です。意識的に補強する価値があります
- ネットワークとセキュリティは土台であり、SREとしての価値はこの上に載る**SLO設計・可観測性・キャパシティプランニング・トイル削減**で決まります

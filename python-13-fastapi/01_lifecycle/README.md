# 01_lifecycle — ライフサイクルとデプロイ安全性

**この章の問い**: デプロイのたびに 502 が出るのはなぜか。

| ファイル | 学ぶこと |
|---|---|
| `lifespan_basics/` | 共有リソースの生成と破棄、起動時に疎通確認をしない理由 |
| `health_endpoints/` | livez / readyz / startupz の分離、readiness に依存を含める判断 |
| `graceful_shutdown/` | シャットダウン4段階の実装、処理中リクエストの待機 |

## 設定値の噛み合わせ（この章の要）

コードだけでは 502 は消えません。以下の4つが噛み合って初めて成立します。

| 層 | 設定項目 | 例 |
|---|---|---|
| ALB | ヘルスチェック間隔 × 異常閾値 | 10 秒 × 2 回 = 20 秒 |
| ALB | 登録解除遅延（deregistration delay） | 30 秒 |
| アプリ | ドレイン待機 + 処理中待機 | 20 秒 + 30 秒 |
| ECS | stopTimeout（Fargate は最大 120 秒） | 90 秒 |

**検算**: アプリが必要とする時間（50 秒）＜ stopTimeout（90 秒）であること。
逆転していると SIGKILL され、処理中のリクエストが切れます。

自分の担当システムの実値を、この表に書き出してください。逆転が見つかれば
それがデプロイ時 5xx の原因である可能性が高いです。

## 合格基準

- [ ] シャットダウン4段階を順序込みで説明できる
- [ ] 上の表を担当システムの実値で埋め、逆転がないか検算した
- [ ] `graceful_shutdown.py` を起動し、`/slow` 実行中に SIGTERM を送って挙動を確認した
- [ ] readiness に DB 疎通を含めるべきかどうかを、自分のシステムについて判断し理由を言える
